# AWS deployment (Terraform + GitHub Actions)

Deploys the app to a single EC2 instance running Docker Compose, with images built and
pushed by GitHub Actions and deploys triggered over SSM (no SSH keys, no long-lived AWS
credentials in GitHub).

## Architecture

- **Compute**: one `t3.micro` EC2 instance (Amazon Linux 2023), running the two containers
  from the root `docker-compose.yml` pattern (rendered as a prod variant with prebuilt
  images instead of `build:`). Reachable only on port 80; no SSH port, no key pair — shell
  access, if you ever need it, is `aws ssm start-session --target <instance-id>`.
- **Images**: two ECR repositories (`todo-list-server`, `todo-list-client`), built and
  pushed by GitHub Actions on every push to `main`.
- **Secret**: `JWT_SECRET` is generated by Terraform (`random_password`) and stored in SSM
  Parameter Store as a `SecureString`. The instance's IAM role can read only that one
  parameter; GitHub Actions never sees the value — see `templates/deploy.sh.tpl`.
- **CI/CD auth**: GitHub Actions assumes an IAM role via OIDC (`iam.tf`), scoped to pushes
  to `main` on this exact repo. No AWS access keys are stored as GitHub secrets.
- **Deploy mechanism**: GitHub Actions pushes new images, then runs
  `aws ssm send-command` to remotely execute `/opt/todo-list/deploy.sh` on the instance,
  which pulls the new images, fetches the current `JWT_SECRET`, and restarts the app. The
  same script runs once at instance boot (via `user_data`) and on every later deploy.

## One-time setup

**Prerequisites**: an AWS account, the [AWS CLI](https://aws.amazon.com/cli/) configured
with credentials that can create IAM roles/EC2/ECR/SSM resources, and
[Terraform](https://developer.hashicorp.com/terraform/install) >= 1.5.

```bash
cd infra
terraform init
terraform apply
```

Review the plan, then confirm. This creates everything described above and prints outputs
at the end, e.g.:

```
deploy_role_arn        = "arn:aws:iam::123456789012:role/todo-list-github-deploy"
aws_region              = "us-east-1"
ecr_server_repository   = "todo-list-server"
ecr_client_repository   = "todo-list-client"
ec2_instance_id         = "i-0123456789abcdef0"
app_url                 = "http://203.0.113.10"
```

The instance takes a couple of minutes after creation to finish its first boot (installing
Docker, pulling nothing yet since no images have been pushed). `app_url` won't serve
anything until the first GitHub Actions deploy has pushed images and triggered a run of
`deploy.sh` — see the next step.

### Wire up GitHub Actions

In the GitHub repo, go to **Settings → Secrets and variables → Actions → Variables** and
add these five **repository variables** (not secrets — none of these values are sensitive
on their own; that's the point of the OIDC setup):

| Variable | Value |
|---|---|
| `AWS_DEPLOY_ROLE_ARN` | `terraform output -raw deploy_role_arn` |
| `AWS_REGION` | `terraform output -raw aws_region` |
| `ECR_SERVER_REPOSITORY` | `terraform output -raw ecr_server_repository` |
| `ECR_CLIENT_REPOSITORY` | `terraform output -raw ecr_client_repository` |
| `EC2_INSTANCE_ID` | `terraform output -raw ec2_instance_id` |

Then push to `main`. `.github/workflows/deploy.yml` will run the test suite, build and
push both images, and trigger the deploy. Watch the run in the **Actions** tab; the final
step's output is the remote script's stdout/stderr, so a failure there tells you exactly
what went wrong on the instance.

Once it succeeds, visit the `app_url` from the Terraform output.

## Updating the secret

```bash
aws ssm put-parameter --name /todo-list/prod/JWT_SECRET --type SecureString --overwrite --value '<new-value>'
```

Takes effect on the next deploy (re-run the GitHub Actions workflow, or
`aws ssm send-command --instance-ids <id> --document-name AWS-RunShellScript --parameters 'commands=["sudo /opt/todo-list/deploy.sh"]'`).

## Tearing down

```bash
terraform destroy
```

## Known tradeoffs

- **Local state contains the secret in plaintext** (it's a Terraform resource attribute).
  Fine for a personal/demo deployment; a team setup should use a remote backend (S3 +
  DynamoDB locking, with encryption) instead of local `terraform.tfstate` — and state files
  must never be committed (already covered by the root `.gitignore`).
- **`user_data` only runs on first boot.** Changing `templates/docker-compose.prod.yml.tpl`
  or `templates/deploy.sh.tpl` later requires either `terraform apply -replace=aws_instance.app`
  (replaces the instance) or manually re-running the updated script over SSM — there's no
  auto-sync mechanism. Intentional simplicity tradeoff for a single-instance setup.
- **Plain HTTP.** No domain or TLS certificate is configured, so credentials are
  unencrypted in transit. Adding a domain + [Caddy](https://caddyserver.com/) (or
  certbot + nginx) for automatic HTTPS is the natural next step if this were exposed to
  real users.
- **No backups.** SQLite lives in a named Docker volume on the instance's root EBS volume —
  durable across stop/start, but gone if the instance is replaced or terminated.
- **Single instance, no autoscaling.** Matches the "most straightforward" goal; a
  production-grade setup would use ECS/Fargate or App Runner behind a load balancer, which
  in turn requires swapping SQLite for RDS (see the root README's "Given more time"
  section — the service layer already isolates all SQL, so this is a contained change).
